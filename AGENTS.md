# Local development lifecycle

- Prefer the root `pnpm dev:*` commands for exploring individual apps. `pnpm dev` (or `pnpm dev:local`) starts the main API/web preview and only the PostgreSQL it needs. `pnpm dev:marketing` and `pnpm dev:evals` need no Docker or Clerk setup. See the command matrix in [local development](docs/operations/local-development.md).
- Use `pnpm dev --help` for the command matrix, `pnpm dev:doctor [app]` for read-only setup/port diagnostics and `pnpm dev:list` for worktree/container/volume inventory. Unknown or unregistered resources are not permission to delete them.
- Run development in the foreground. Ctrl+C stops the supervisor's app process groups and its owned `--rm` database container; named database data is retained. Use `pnpm dev:status` and `pnpm dev:stop [app]` to inspect, stop, or recover this worktree's managed sessions. Do not start background services for handoff.
- When containers are needed, use `docker run --rm` or `docker compose run --rm` for temporary jobs. A detached container does not stop when an agent finishes: always stop resources you started, including after verification fails. Use the lifecycle commands instead of ad hoc detached stacks.
- Before handing back, save screenshot/video evidence, then stop every server/container you started. Return the exact commands the user can run to restart the relevant app and close it (usually Ctrl+C or `pnpm dev:stop`). Reused services owned by the user or another session must be preserved.
- Never use global Docker pruning or delete database volumes during ordinary verification. `pnpm dev:clean` retains data; `pnpm dev:clean --data` explicitly deletes only the generated development database for this worktree. Disposable test commands clean up their own containers, data, networks, and generated images.

# Local browser verification

For web behavior or appearance changes, use the real local application to verify the result and return saved screenshot/video evidence when browser tools are available. The workflow is documented in [local development](docs/operations/local-development.md#agent-browser-verification-in-a-worktree).

- In a fresh worktree, run `pnpm install --frozen-lockfile`, then `pnpm dev:setup`. Setup stops its temporary container on completion and prepares a separate empty database and imports only development Clerk keys from the main checkout's ignored `.env`. When sample data is needed, manually run `pnpm example:seed --email askesis-verification+clerk_test@example.com`.
- Run `pnpm dev:local` and use the printed Vite address. In another terminal, `pnpm --silent dev:login` returns JSON with a login `url` for the dedicated verification account. Open it in the same browser tab used for verification; no human sign-in is needed.
- Check that the web URL responds and `/api/ready` on the configured API port returns HTTP 200 before diagnosing browser or Clerk failures. After a reboot or stopped session, restart this worktree with `pnpm dev`. Reuse healthy servers for this worktree; do not start duplicate listeners or assume another worktree's server contains your changes.
- Check readiness before capturing evidence. After recording, stop the preview with Ctrl+C or `pnpm dev:stop local`; confirm `pnpm dev:status` has no sessions you started. Return the saved evidence, actual local URL, and `pnpm dev`/Ctrl+C restart and stop instructions. Do not leave a preview running for the user.
- Confirm the active account is `askesis-verification+clerk_test@example.com` before mutations. Shared browsers may already have another development session; if that account remains active, sign out in Settings and use a fresh login link.
- Prefer T3's `preview_*` tools. Call `preview_status` and `preview_open` first, then navigate to the login URL. A hidden tab (`visible: false`) can still support automation; inspect the page before concluding the browser is unavailable. Wait for the clean `/plan` URL and sample data before recording. The three example plans start on the previous Monday and each cover twelve weeks. Historical Cardiff, triathlon and Hyrox test fixtures, when explicitly loaded, remain dated 11–24 May 2026; inspect the selected plan's actual dates.
- Exercise the changed interaction and relevant reload behavior. Wait for API-backed content, including workout prescriptions, to finish loading before taking the final screenshot. A server response or passing unit tests alone does not establish that the UI works. State which interactions were verified and any remaining limitations.
- Save screenshots with `preview_snapshot` (`save: true`), and videos with `preview_recording_start`/`preview_recording_stop`. Include the saved artifact paths in the final response. If the browser tools fail, report that limitation accurately.
- Keep login URLs, Clerk handshake parameters, session tokens and secret keys out of committed files and returned evidence. Retain real Clerk/API authorization; do not add an auth bypass to solve local access.
- Stop only processes and Compose resources started for your worktree. The generated `.env` selects a separate Compose project and volume. Do not reset another worktree's database.

# Coaching prompt versions

- Any change to the coaching prompt text in `apps/agent/src/prompt.ts` bumps `PROMPT_VERSION` to the next `coach-vN` (for example `coach-v1` → `coach-v2`). Change only the number: keep the `coach-vN` naming and leave earlier versions' entries untouched.
- Bump once per PR relative to `main`. If the prompt changes again before the PR merges, keep the new name and update its hash.
- Update the API's copy of the name in `apps/api/src/modules/agent/agent.schemas.ts`, add the name and hash to `apps/agent/prompts.lock.json` (the test failure prints the hash to use) and replace the old name in tests and docs. Workers and the API must be deployed together.
